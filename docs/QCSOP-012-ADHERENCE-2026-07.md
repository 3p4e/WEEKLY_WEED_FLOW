# QCSOP 012 v3 — Certificate (CoA / CoQ) Adherence Assessment & Plan Forward

**SOP:** QCSOP 012 v3.0 — *Standard Operating Procedure for Certificate of Analysis and
Certificate of Quality — Issuance and Management* (+ QCSOP012A01 v01 workflow flowcharts).
**Assessed:** 2026‑07‑21, against live backend `weekly_weed_flow-backend:v75` /
`backend/app/api/qc.py` (certificate surface) and the `qc_certificates` / `qc_results` /
`qc_coa_documents` / certificate‑register model.
**Governing authority:** where the app and the SOP disagree, the SOP is the regulatory
truth. GxP guardrails already in the app (never fabricate a value; issued records
immutable; forward‑only numbering; reviewer ≠ analyst; QP‑gated release) are preserved by
every recommendation below.

---

## 1. What the SOP mandates (the model)

QCSOP 012 v3 controls **three distinct certificate records** and one master register:

| Record | Definition | Scope |
|---|---|---|
| **iCoA** (internal CoA) | Primary record of **one analytical event on one identified sample**, generated by the QC lab. Signed by the analyst + Head of QC. | §6.2 |
| **eCoA** (external CoA) | A CoA **received from an external contract lab** for one analytical event. | §6.3 |
| **CoQ** (Certificate of Quality) | A QC‑internal document that **aggregates all iCoA + eCoA results for one batch** into a single specification‑conformance summary, **as an input to the QP batch‑release decision**. Explicitly **NOT** an Annex‑16 release certificate; **carries no QP signature.** | §6.4 |
| **Certificate Issuance Register** (QCT 017) | The controlled master log listing **every** iCoA, eCoA, and CoQ with a strict per‑type, per‑year, monotonic number. | §6.13 |

Key mandated controls:

- **§6.2 iCoA** — drafted the same working day the last result is available; fields = sample
  ID (verbatim), sampling date+location, analysis date(s), spec ref (doc + version effective
  on the test date), method per test, results table (param, method, acceptance criterion,
  result+units+sig‑figs, Conforms Y/N), overall conformance statement, comments. HoQC reviews
  vs the source package (transcription, recalculation, near‑limit discussion) → signs
  "Reviewed and Approved by QC Manager" → becomes a controlled record via a **Register entry**.
- **§6.3 eCoA** — received via a secure channel; **provisional register entry (status
  Pending Review)**; internal cross‑ref `eCoA‑PP‑YYYY‑NNNN`; original file + metadata stored;
  **mandatory review within 5 working days** against the **External CoA Review Checklist
  (QCT 018 / Annex A03)** — a first‑class record whose fields are the single source of truth.
  **Conformance is determined by Purely Plant, never taken from the eCoA.** Discrepancies
  resolved in writing before acceptance; on acceptance QC Manager signs the checklist →
  status **Accepted**. Rejected eCoAs are **voided** and replaced.
- **§6.4 CoQ** — compiled for **every FP batch and every intermediate bulk batch for QP
  release**. Prerequisites: **all** spec params tested, **all** iCoAs approved, **all** eCoAs
  accepted, **no open OOS**. Aggregated results table = **one row per spec parameter, citing
  the source certificate number (iCoA/eCoA) and the testing lab**; plus a source‑certificate
  list (every iCoA/eCoA number + issue date). Signed **"Compiled by"** (Senior QC Analyst /
  Head of Lab), then **"Reviewed and Approved by HoQC"** by the QC Manager → controlled record
  + register entry → **released into the QP batch‑release dossier (no QP signature on the
  CoQ).**
- **§6.5 OOS on certificates** — a cert is **not withheld** pending investigation; it is
  issued as the objective record with "Out of Specification — [param]" + the OOS investigation
  cross‑ref in comments; a retest gets a **new** cert referencing the original (both retained);
  a **CoQ is not compiled for a batch with an open OOS.**
- **§6.6 Correction/Revision/Reissuance** — approved certs are never edited; a change is a
  **revised** cert (new number, status **Revised**, "Supersedes [orig] — reason"), the
  original → **Superseded**; a fundamentally invalid cert (wrong batch / wrong sample) is
  **Voided** with written HoQC authorization, the original archived with the voiding decision.
- **§6.7 Language** — English is the **primary controlled language**; a bilingual EN/MK
  version is issued **only** where required by customer/customs/regulator, and a translation is
  verified by a second qualified reviewer; **English prevails**.
- **§6.13 Register** — fields (cert #, type, issuing lab, sample ID + batch, product/material,
  spec ref+version, sampling/analysis/issue dates, analyst, reviewer, status ∈ {Draft, Issued,
  Accepted, Revised, Superseded, Voided}, supersession xref, OOS xref, retention start, archive
  location). **Per‑type, per‑year, strictly monotonic numbering — no skip/reuse/reassign;
  gaps are investigated as ALCOA+ data‑integrity events.** Reporting: by quarter/type/lab;
  Draft/Pending; OOS‑linked; end‑of‑retention.
- **§6.16 Deviations** — CoQ for an open‑OOS batch, editing an approved cert, a register
  gap/duplicate, or retention loss are logged as deviations under QASOP 010.

## 2. What the app implements today

- `qc_certificates` — one entity with `coa_number = PP‑COA‑YYYY‑NNNN`,
  `cert_type ∈ {ICOA, ECOA, COQ, WATER, OTHER}`, lifecycle
  `DRAFT → REVIEWED → APPROVED → RELEASED (+ SUPERSEDED)`, `decision ∈ {PASS, FAIL}`,
  `analyst_id`, `laboratory_id`, `supersedes_id`/`revision_reason`, `retention_start`/
  `retention_expiry`/`archive_ref`, `coq_document_id`. Reviewer ≠ analyst enforced;
  APPROVED/RELEASED are QP‑gated (`qc.py:735‑748`).
- `qc_results` — per‑parameter rows (param link, limits, `complies`, provenance
  `source_document_code/date/institution` from an eCoA promotion).
- `qc_coa_documents` — the **eCoA ingestion spine** (`PP‑ECOA‑YYYY‑NNNN`,
  `UPLOADED → EXTRACTED → REVIEWED → PROMOTED/REJECTED`, 5‑working‑day `review_deadline`,
  PDF original + SHA‑256, adaptive placeholder discovery). Server‑side grading — the app
  **never trusts the eCoA's own verdict** (`qc.py:2119‑2132`).
- **CoQ** — `POST /qc/certificates/{id}/coq` renders **one RELEASED `qc_certificate`** to a
  bilingual house‑style `.docx` via the DocEngine, gated by: all results comply (409),
  a mandatory‑content manifest, an **open‑OOS block**, and a `pp_verify` PASS gate
  (`qc.py:generate_coq`).
- **Register** — `GET /register` (filter by quarter/type/lab; pending; OOS‑linked;
  end‑of‑retention) + `GET /register/gaps` (numbering‑gap report) (`qc.py:1652‑1764`).
- Annex‑11 e‑signatures captured on the certificate; supersession chain on revise/release.

## 3. Clause‑by‑clause adherence

Legend: **FULL** = met · **PARTIAL** = data present but semantics/controls incomplete ·
**GAP** = not implemented · **DIVERGENT** = app deliberately differs.

| # | SOP clause | Requirement | App state | Verdict |
|---|---|---|---|---|
| 1 | §Defs / §6.4 | **CoQ = per‑batch aggregation of all iCoA+eCoA, input TO the QP release decision** | CoQ is a `.docx` rendered from **one** already‑`RELEASED` cert, **after** QP release, not an aggregation across a batch's source certs | **GAP (structural, headline)** |
| 2 | §Defs | iCoA / eCoA / CoQ are **three distinct records** in one register | `cert_type` enum exists, but eCoAs live in a **separate** `qc_coa_documents` table; CoQ is a render, not a record; register lists `qc_certificates` only | **PARTIAL** |
| 3 | §6.2.2 | iCoA fields (sample ID, sampling date+location, analysis date range, spec ref+version, method/param, acceptance criterion, result+units+sig‑figs, Conforms Y/N, statement, comments) | Most captured (`qc_results`, spec link, `method`); **sampling location** only on the sample (join), **analysis date is a single `report_date`** not a range | **PARTIAL** |
| 4 | §6.2.3 | Second‑person HoQC review + documented return‑to‑analyst | Reviewer ≠ analyst enforced; QP‑gated; e‑sign captured. No structured verification **checklist**; no explicit "return to analyst with comments" transition | **PARTIAL** |
| 5 | §6.2.1 | iCoA drafted **same working day** last result is available | Not tracked | **GAP (low)** |
| 6 | §6.3.1 | eCoA provisional register entry (**status Pending Review**) + `eCoA‑PP‑YYYY‑NNNN` + original file+metadata + **5‑working‑day** review clock | Register entry + `review_deadline` + PDF original + SHA‑256 present; statuses use `UPLOADED/EXTRACTED/REVIEWED/PROMOTED`, number is `PP‑ECOA‑` not `eCoA‑PP‑` | **PARTIAL** |
| 7 | §6.3.2 | Mandatory review vs **External CoA Review Checklist (QCT 018)** as a first‑class record; **conformance determined by PP** | Server grades every value (PP determines conformance — **aligned**); but there is **no structured QCT 018 checklist record** with per‑field completion + a checklist signature | **PARTIAL** |
| 8 | §6.4 (prereq) | CoQ prerequisites: all params tested · all iCoAs approved · all eCoAs accepted · no open OOS | Open‑OOS block ✓, all‑results‑comply ✓, completeness manifest ✓; "all **iCoAs**/**eCoAs**" is not a multi‑cert prerequisite (one cert) | **PARTIAL** |
| 9 | §6.4 (table) | CoQ aggregated table = **one row per spec param citing its source certificate number + testing lab** | A result may carry one `source_document_code` (if promoted from an eCoA); internal results cite no iCoA number; no cross‑cert aggregation | **GAP** |
| 10 | §6.4 (sign) | CoQ **"Compiled by"** (Senior Analyst) then **"Reviewed by HoQC"**; **no QP signature** | E‑sign block rendered; CoQ is not a separately compiled+reviewed record; comment notes QP "receives" it — intent aligned, ordering inverted (see #1) | **PARTIAL** |
| 11 | §6.5 | Cert issued (not withheld) with OOS statement + investigation xref; retest = new cert referencing original; no CoQ on open OOS | Open‑OOS blocks CoQ ✓; supersession for retests ✓; OOS xref surfaced in the register ✓ | **FULL / PARTIAL** |
| 12 | §6.6 | Revised cert (new #, status **Revised**, "Supersedes… reason"); original → **Superseded**; **Voided** for fundamentally invalid certs (written HoQC auth) | Revise → supersede chain **FULL**; **no `VOIDED` state** | **PARTIAL — Void missing** |
| 13 | §6.7 | English primary; bilingual **optional** on demand; translation verified by 2nd reviewer; English prevails | CoQ is **always** bilingual MK+EN; no English‑primary flag / translation‑verification step | **DIVERGENT (app does more)** |
| 14 | §6.13 (fields) | Register field set | Nearly complete (`coa_number`, type, lab, batch, sample, spec, dates, analyst, reviewer, status, `supersedes_id`, retention, archive_ref, OOS xref) | **FULL** |
| 15 | §6.13 (numbering) | **Per‑type, per‑year, strictly monotonic**; gaps = DI events | `qc_coa_id_seq` is **one shared global sequence** for all cert types, **never resets per year**, and is **shared cross‑tenant**; a gap report exists but numbering is not per‑type/per‑year | **GAP** |
| 16 | §6.13 (status) | Status ∈ {Draft, Issued, Accepted, Revised, Superseded, Voided} | App uses {DRAFT, REVIEWED, APPROVED, RELEASED, SUPERSEDED} — no Voided / Accepted / Issued mapping | **PARTIAL** |
| 17 | §6.8/§6.15 | Retention start + archive location + fire‑resistant controlled storage | `retention_start/expiry/archive_ref` + PDF custody + SHA‑256 | **FULL (data)** |
| 18 | §6.16 | Deviations logged per QASOP 010 (CoQ‑on‑open‑OOS, editing approved cert, register gap, retention loss) | App **prevents** these (blocks) rather than **logging** them as deviations | **PARTIAL** |

**Headline:** the app is strong on the *records‑management data* (register, retention, PDF
custody, server‑side grading, second‑person review, OOS blocking, supersession) but diverges
on the **CoQ relational model** (#1, #9), on a few missing **states/controls** (Void #12,
per‑type/per‑year numbering #15, the QCT 018 checklist #7), and on the **iCoA/eCoA/CoQ
three‑record split** (#2).

## 4. Plan forward — dependency‑ordered, additive, non‑breaking

Every increment follows the established house pattern: **delta‑first → one additive raw‑SQL
migration (facility canon: uuid PK + org_id, FORCE/ENABLE RLS, `audit_<tbl>` trigger, guarded
GRANT) → backend router → frontend view → tests → full local gate (pytest + schema‑drift +
migration up/down/base + node --check) → adversarial review → deploy both stacks → live
smoke → DEPLOY.md.** GxP invariants (never fabricate; issued records immutable; forward‑only
numbering; reviewer ≠ analyst; QP‑gated) hold throughout. Nothing here deletes or renumbers an
issued record.

### Tier 1 — compliance‑critical, low‑risk, additive (recommended first)

**C1 — Voided state + certificate correction discipline (§6.6, #12).**
Add `VOIDED` to `_COA_STATUSES`; a QP/HoQC‑only `POST /qc/certificates/{id}/void`
requiring a written reason; a `void_reason` + `voided_by`/`voided_at`; the original stays
archived (never deleted). Register/status vocabulary gains Voided. Small migration; 1 endpoint;
frontend button on qccoa‑view.

**C2 — Per‑type, per‑year, monotonic certificate numbering (§6.13, #15).**
Replace the shared global `qc_coa_id_seq` with **advisory‑locked per‑(org, cert‑type, year)**
sequential numbering (the exact pattern already used for the RQS ordinal in QCSOP 011):
`iCoA‑PP‑YYYY‑NNN`, `eCoA‑PP‑YYYY‑NNN`, `CoQ‑PP‑YYYY‑NNN`, reset 001 on 1 January.
**Forward‑only** — existing `PP‑COA‑*` numbers are immutable and remain valid; the new format
applies to newly issued certs only. Upgrade `/register/gaps` to be per‑type/per‑year and to
emit a **deviation event** (not just a report row) on a detected gap (§6.16).

**C3 — External CoA Review Checklist as a first‑class record (QCT 018, §6.3.2, #7).**
New `qc_ecoa_checklist` child of `qc_coa_documents`: the SOP's review fields (sample‑ID match,
method‑per‑TQA, units‑per‑PP‑spec, per‑parameter PP conformance determination, discrepancy
flags), per‑field completion, reviewer signature, and an explicit **Accepted / Rejected**
outcome. The existing server‑side grading feeds the conformance column (PP determines it).
Aligns eCoA statuses to the SOP vocabulary (**Pending Review → Accepted / Rejected**).

**C4 — Register + status‑vocabulary unification (§6.13, #2, #16).**
Surface eCoA *documents* and (from C5) CoQs in the **same** `/register` view as a single
Certificate Issuance Register spanning iCoA + eCoA + CoQ; add the SOP status labels
(Draft/Issued/Accepted/Revised/Superseded/Voided) as a presentation mapping over the internal
lifecycle. Add the missing register queries already named by the SOP (per‑quarter export).

### Tier 2 — the CoQ structural model (its own plan; larger)

**C5 — CoQ as a per‑batch aggregation record that feeds QP release (§6.4, #1, #9, #10).**
The one architecturally significant change. New `qc_coq` entity (per batch:
`coq_number = CoQ‑PP‑YYYY‑NNN`, batch/product/manufacture‑date/size, spec ref+version,
`compiled_by`, `reviewed_by`, status) + `qc_coq_sources` (m:n link to the contributing iCoA /
eCoA certificates, each with its cited number, issue date, and testing lab) + `qc_coq_lines`
(one row per spec parameter citing its **source certificate**). A `POST /qc/coq` **compile**
endpoint that: enforces the four prerequisites against the batch's *set* of approved iCoAs +
accepted eCoAs; builds the aggregated table with source‑cert citations; captures "Compiled by".
A review/approve step captures "Reviewed by HoQC" — **no QP signature**. The CoQ `.docx`
renders from this aggregation, and the CoQ becomes the **input to** the QP batch‑release
decision (re‑ordering CoQ *before* release, per §6.4), while the existing single‑cert CoQ
render stays available for backward compatibility until cutover. This supersedes today's
"render CoQ from a released cert" flow; plan it as a standalone increment with a data‑model
review and an owner decision on cutover.

### Tier 3 — polish (low priority)

**C6 — iCoA field completeness (§6.2.2, #3):** analysis‑date range (start/end) and a
sampling‑location echo onto the cert; **same‑working‑day** draft timeliness flag (§6.2.1, #5).
**C7 — English‑primary language model (§6.7, #13):** an issue‑language flag (English default,
bilingual on demand) + a translation‑verification (second‑reviewer) capture; keep bilingual as
the default output.
**C8 — Deviation auto‑logging (§6.16, #18):** where the app currently *blocks* a
non‑compliant action (CoQ on open OOS, editing an approved cert, a numbering gap), also emit a
QASOP‑010 deviation event for the record, not just a 4xx.

### Sequencing & effort

- **Tier 1 (C1–C4)** is four small, additive, non‑breaking increments — each a single
  migration + endpoint(s) + view + tests, deployable in a day, closing the discrete
  compliance gaps (Void, numbering, checklist, register). **Recommended immediate scope.**
- **Tier 2 (C5)** is the real structural work (a new aggregation entity + re‑ordering CoQ
  before release). It deserves its own delta‑first plan and an explicit owner decision on the
  cutover from the current single‑cert CoQ render. **Recommended as a dedicated follow‑on.**
- **Tier 3 (C6–C8)** is cosmetic/records polish — fold in opportunistically.

### Out of scope (recorded, not acted)

Paper‑archive physical controls (§6.8 fire‑resistant storage) are facility controls, not app
features. The A3 paper MLR logbook (QCSOP 001 §6.8.3) is intentionally paper‑only. QP batch
release itself is governed by a separate SOP (Annex 16) — the app only produces the CoQ *input*.
