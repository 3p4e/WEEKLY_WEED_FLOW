### DI2-01 [high] correctness/ops — The CI `compose` job fails at HEAD: `.env.example` ships an empty `CAPTURE_IMPORT_TOKEN`, `docker compose config` refuses it, so CI is red and `deploy.yml` will refuse every commit on this branch
**Where:** `.env.example:112` (`CAPTURE_IMPORT_TOKEN=`, emptied by f7c1a38 for BC-11); `docker-compose.yml:276` (`${CAPTURE_IMPORT_TOKEN:?set in .env}`); `.github/workflows/ci.yml:485-494` (`cp .env.example .env && docker compose config`); `deploy.yml:159-223` (CI-green gate, "deliberately NOT skippable").
**What happens:** Compose's `${VAR:?msg}` fails on an unset **or empty** variable. The `compose` job copies the template verbatim, so it now aborts with `required variable CAPTURE_IMPORT_TOKEN is missing a value`. Every PR run of `ci.yml` at HEAD (including PR #52, whose run 36306334208 was still queued when checked) ends with a red check; `deploy.yml`'s first step then refuses the SHA, and the branch that carries every review fix cannot be shipped through the workflow. (`ops/agent/rsh.py` hand deploys are unaffected, but `docs/HANDOFF.md:56-75` plans the rollout on the workflow sequence.) The seam: a backend-workstream template change met the infra compose guard; neither side's tests copy the template into compose.
**Evidence:** Reproduced in the scratchpad with the repo's `docker-compose.yml` and `.env.example` copied to `.env` (`docker compose config` v5.1.1 → rc=1, the error above); with `CAPTURE_IMPORT_TOKEN=change-me` → rc=0. `git show f7c1a38 -- .env.example` shows `-CAPTURE_IMPORT_TOKEN=change-me` / `+CAPTURE_IMPORT_TOKEN=`.
**Fix:** Put `CAPTURE_IMPORT_TOKEN=change-me` back in `.env.example` — `backend/app/config.py:36-37, 125-137` already treats `change-me` (and anything under 32 chars) as UNSET, so the BC-11 guarantee holds while the compose guard is satisfied. Alternatively have the `compose` job append a dummy value after the `cp`. Either way, also assert in `ci.yml` that the template plus compose validate together (they do once the value is back).

### DI2-02 [medium] correctness/data-integrity — `reap_orphaned_jobs` is per-process, so two uvicorn workers fail each other's live jobs every five minutes; the Dockerfile still says two workers are safe
**Where:** `docengine/app/db.py:22` (`WORKER_ID = … uuid.uuid4().hex` per process), `:170-183` (`worker_id IS DISTINCT FROM $1`, no age check); `docengine/app/main.py:53-75` (both reapers at startup and every 300 s); `docengine/Dockerfile:24-27` ("2 workers are safe for that too (H13)"), `:40` (`--workers 1`).
**What happens:** With `--workers 2` (or any second process on the same database — a staging copy, an operator running the app by hand against production's DSN), each process boots with its own `WORKER_ID`. Process A's periodic sweep sees every job B created (`worker_id = B ≠ A`, status running) and marks it `failed: abandoned: worker B is gone` while B's task is mid-generation; B does the same to A. Every job on the service dies within five minutes of starting, with an error text that blames a redeploy. The startup sweep already does this on the first boot of a second worker. The `exclude=` shield covers only the stale sweep, not the orphan sweep. Nothing enforces one worker except the CMD string, and the Dockerfile's own comment invites raising it.
**Evidence:** Read both reapers and the sweep; `_running_jobs` is consulted only for `reap_stale_jobs` (`main.py:62`); the orphan query has no exclusion. `test_db.py:223-244` pins exactly the behaviour that becomes destructive under two workers.
**Fix:** Make the id per container boot rather than per process: create it once with `O_EXCL` in a tmpfs path that does not survive a container restart (`/dev/shm/docengine-boot-id`) and have every worker read it; or keep the per-process id but run the orphan sweep only at startup and only for rows older than the process's own start time. In either case delete the "2 workers are safe" sentence in the Dockerfile and say the reaper requires one process per database.

### DI2-03 [medium] data-integrity/canon — A second revision of the same document registers the same code+version again (the DI-07 defect one level up); nothing in the registry is unique
**Where:** `docengine/app/pipeline.py:1310-1312` (`meta["version"] = _bump_version(source_meta…)`, derived from the source only); `docengine/app/db.py:34-74` (no unique index on `(org_id, code, version)`); `main.py:427-459` (`/revise` accepts the same source job any number of times).
**What happens:** SOP-X v1.0 (job J) is revised with "tighten" → row SOP-X/1.1 supersedes v1.0. The author is unhappy and revises J again with "simplify" → a second row SOP-X/1.1, different bytes, also superseding v1.0. `/documents` now lists two controlled documents with one identity and no ordering between them; `supersedes_id` says both replace v1.0 and neither replaces the other. The first review's complaint was "the same code/version with different bytes is a document-control defect in a GMP registry"; the fix moved it from `1.0` to `1.1`. `/build` has the same property by design (every CoQ regeneration registers `PP-COA-n/01` again), which is accepted for certificates but not for SOPs.
**Evidence:** `_bump_version` takes only the source's version; `run_revision` never reads the registry; `grep -n unique docengine/app/db.py` is empty. `test_pipeline.py:1355-1387` asserts `1.1` for one revision and nothing about a second.
**Fix:** In `run_revision`, take the next version from the registry — `MAX(version)` for `(org_id, code)` among rows whose version has the same shape — or refuse (409 at `/revise`) when the source document already has a successor, so a revision-of-a-revision must start from the latest row. Add `CREATE UNIQUE INDEX IF NOT EXISTS de_docs_identity ON docengine.documents(org_id, code, version) WHERE source <> 'build'`.

### DI2-04 [medium] security/attribution — `/qms/studio/build` forwards the browser's `requested_by` unchanged, so a Studio direct build is registered as whoever the client claims (usually nobody), and no audit event is written
**Where:** `backend/app/api/qms.py:151-159` (`studio_build` forwards `body` as received; compare `:101` and `:147` where workflows and revisions stamp `body["requested_by"] = user["username"]`); `docengine/app/main.py:539-561` (stores `created_by = body.requested_by`); `web/gf/qmsstudio-view.js:190-196` (sends none).

### DI2-05 [medium] data-integrity/ops — The offsite rotation still runs when the copy failed, so a remote that accepts deletes but not uploads ages to empty in 60 days; and a lost `docengine_out` mount never rises above WARN
**Where:** `backend/scripts/offsite_backup.sh:39-53` (the `rclone copy` result is only logged; `rclone delete --min-age 60d` is gated on local freshness alone); `backend/scripts/db_backup.sh:72-84` (absent mount → warning, `ok` stays 1, rotation proceeds); `ops/watchdog.sh:596-603` (`docengine_out=none` → WARN "no DocEngine archive yet").
**What happens:** (1) Drive quota exhausted or the OAuth token revoked for uploads while `delete` still succeeds (rclone's delete is a separate API call that can succeed when uploads are rejected): every cycle logs `COPY FAILED`, the local dump is fresh so the guard passes, and `rclone delete` keeps trimming the remote. After 60 days the offsite set is empty exactly as DI-10 described, with a different trigger. The watchdog's `offsite_fresh` would FAIL after 48 h — but `HANDOFF.md` records that no alert channel is configured, so `docker logs` is the only signal. (2) If the read-only mount is dropped from `db-backup` (a compose edit, a recreate from an older file), `db_backup.sh` warns and rotates: after 14 days there is no local document archive, after 60 no remote one, and the watchdog reports WARN forever because "none" is treated as "not deployed yet".
**Evidence:** Read both scripts and the watchdog case arm; `sh -n`/`bash -n` clean. The first review's fix said "skip `rclone delete` unless the newest local dump is under 30 h old" and that is exactly what landed; the copy-failed case is the one it does not cover.
**Fix:** Track `copy_ok=1/0` and skip the delete when the copy failed; additionally require the newest **remote** object (`rclone lsl … | sort | tail -1`) to be younger than `LOCAL_FRESH_MAX_S` before deleting. In `db_backup.sh` make the missing mount `ok=0` once a `docengine_out_*.tar.gz` already exists in `/backups` (so a stack that never had the mount still rotates); in the watchdog FAIL on `none` when the DocEngine container is running.

### DI2-07 [low] correctness — `_qa_audit_passed` still passes a single-line "PASS with the following blocking issue …", and its verdict regex crosses line breaks
**Where:** `docengine/app/pipeline.py:466-468` (the single-line concession: no verdict line, no newline, starts with PASS, no `FIX` token); `:302-305` (`\s*` between `verdict`, the separator and the token — `\s` matches `\n` under `re.M`).
**What happens:** A model that ignores the "Verdict:" format and answers in one line — `PASS with the following blocking issue: 3.0 is missing the QP role`, `PASS, except the QP role is missing in 3.0 — must be fixed before release`, `PASS but section 3 must be FIXED` — passes the gate (all three returned True).
