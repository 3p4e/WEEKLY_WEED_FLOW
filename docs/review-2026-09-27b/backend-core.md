### R2-BC-01 [medium] contract — The UI still hides every waste/decon/gowning record action from the production manager the backend now admits (BC-12 unreachable end to end)
**Where:** `web/gf/waste-view.js:75` (`canRecord = () => ['ADMIN','OWNER','CEO','COO','CU_MGR']`), `web/gf/decon-view.js:42` (`canClean`, same list) versus `backend/app/api/waste.py:66` `_RECORDERS = (ADMIN, *EXECUTIVE_ROLES, "CU_MGR", "PR_MGR")`, `decon.py` `_CLEAN_WRITERS`, `biosecurity.py` `_RECORDERS`.
**What happens:** A PR_MGR opens the waste register or the decon board and sees the read-only rendering: no "New manifest", no add-line/seal/dispose, no cycle/step/bleach/tool-log/gowning entry (`waste-view.js:112,120,234,322,365-601` and the `canClean()` gates all key on that list). Decision A-2 ("PR_MGR records waste manifests and runs decon / gowning for `dry` rooms") is therefore true of the API only; from the app the post-harvest crew is exactly where BC-12 left it — asking the cultivation manager to sign.
**Evidence:** grep of the two views for role lists; the backend tuples and their tests (`test_waste.py::test_production_manager_records_manifests`, `test_decon.py::test_production_manager_cleans_dry_rooms_only`); the frontend commits since 549b617 (`8c6a5bc`, `b2a7638`, `0c2da3f`) do not touch those lists.
**Fix:** Add `'PR_MGR'` to `canRecord` in `waste-view.js` and to `canClean` in `decon-view.js` (and the biosecurity record gate if it has one); leave the room-kind rule to the backend's 403, or filter the room picker to `kind === 'dry'` for that role. ### R2-BC-02 [medium] data-integrity/contract — The audit viewer still pages with `before`, so the row loss BC-08 describes is unchanged for the person reading the trail
**Where:** `web/gf/audit-view.js:79` (`st.before = null`), `:88-89` (`q.before = st.before`), `:115` (`st.before = last row's created_at`); `web/gf/api.js:527` `audit(q)` returns the parsed body only, so `X-Next-Cursor` (`backend/app/api/audit.py:196-199`) is never read.
**What happens:** Same scenario as BC-08: a page of 100 ending inside one transaction's rows (plant generation writes 50 with one `created_at`) is followed by `created_at < before`, which skips the rest of that group permanently. The backend fix is complete and tested, but no client uses it; the file's own "RESIDUAL RISK" comment (`:100-113`) still describes the open bug. A-7 records that `before` stays "until the audit view switches" — it has not switched.
**Evidence:** read both files at HEAD; `git log 549b617..HEAD -- web/gf/audit-view.js` shows only unrelated edits.
**Fix:** Give `api.js` an `auditPage(q)` that returns `{rows, next: res.headers.get('X-Next-Cursor')}` (same-origin, no CORS exposure needed), replace `st.before` with `st.cursor`, send `cursor` instead of `before`, and delete the RESIDUAL RISK comment. Then drop `before` from the backend.

### R2-BC-03 [low] security — Containers on `traefik_network` can inject `X-Forwarded-For` through the frontend's Traefik-side interface (the spoof the compose comment was written to prevent)
**Where:** `web/nginx.conf:23-26` (`map $server_addr … default $http_x_forwarded_for`); `docker-compose.yml` `frontend.networks: internal + traefik`, `capture-mcp.networks: [internal, traefik]` (also RAGflow/Letta and any other stack Traefik publishes).
**What happens:** The map trusts the header on any request that did not arrive on `172.16.31.20`, on the premise that only Traefik reaches the other interface. Every container on `traefik_network` reaches it too. A compromised `wwf-capture-mcp` (the internet-exposed connector the `FORWARDED_ALLOW_IPS` comment names as the threat) connects to the frontend's `traefik_network` address and sends `X-Forwarded-For: <fresh address each time>` → nginx forwards it unchanged → uvicorn trusts nginx and takes that address → the per-IP login bucket never fills and `login_failed`/request logs carry forged addresses. Before f7c1a38 this was impossible: `$proxy_add_x_forwarded_for` appended the real peer and uvicorn took that. The per-account bucket (8 failures / 5 min) still holds, which is why this is low.
**Evidence:** nginx `map`/`proxy_set_header` semantics and the compose network membership; not reproduced against a running stack.
**Fix:** Key the trust on Traefik itself rather than on the interface: `map $remote_addr $wwf_client_xff { <traefik's traefik_network IP> $http_x_forwarded_for; default ""; }` (the owner can read it with `docker network inspect traefik_network`, or give Traefik a fixed address there), or have Traefik add a secret header (`headers.customRequestHeaders`) and gate the map on it. Also record in `test_hardening.py` which of the two the config uses.

### R2-BC-04 [low] authz — A pending handoff gives the receiving manager write scope on a task still in the source department, and a subtask attached during that window keeps it visible after the handoff is rejected
**Where:** `backend/app/api/tasks.py:89` (the `h.status='proposed' … to_dept_id = ANY(dept_family)` arm of `_assert_scope_visible`) — the guard every write path calls: `update_task:722`, `add_progress`, `add_session`, `workflow_transition`, `collab.add_comment/assign/unassign`, and `create_task:508` (`await _assert_scope_visible(c, str(body.parent_id), user)` for a foreign parent).
**What happens:** QC_MGR proposes a QC task to Cultivation. Before anyone accepts, CU_MGR can PATCH its status, title, due date, log sessions on it and sign it off (`workflow_transition` only checks `ELEVATED_ROLES` + scope). Worse for durability: CU_MGR posts a subtask in Cultivation under it (allowed because the parent is "visible"); after the handoff is rejected, the parent stays in CU_MGR's read and write scope through the "child in my family" arm (`tasks.py:87`) — the "closed again once it is resolved" claim in da0498d and A-9 no longer holds for that task. The department-move guard itself is not affected (`src_ok` still fails).
**Evidence:** read the guard arms and the call sites; `test_collab.py::test_handoff_reaches_the_receiving_manager…` checks read visibility returns to 404 after rejection but never attaches a child first.
**Fix:** In `create_task`'s foreign-parent branch, evaluate visibility without the handoff arm (a small `_assert_scope_visible(..., include_handoffs=False)`), and consider limiting the pending-handoff arm to reads plus comments (the handoff routes already have their own authority check). Record whichever is chosen next to A-9.

### R2-BC-05 [low] info-leak — An @mention still delivers title + preview to a department-scoped manager of another department who cannot open the task (BC-17 residual)
