## 2. Must fix — the high-severity findings, deduplicated

### 2.1 The official product catalogue is only half built — and PR #52 said otherwise
`QC-04`, `INS-01`, `INS-02` · verified

The owner's 2026-09-05 decision made the ImB product pages the single live
potency specification and retired the August ladders. What exists: the
`qc_products` table, the import/approve/supersede API, and `product_id` stored
on a CoQ. What does not exist:

- CoQ grading never reads the product. `_coq_disposition`
  (`coq_aggregation.py:92-124`) grades only from a frozen ladder. A CoQ
  compiled with a product prints **no grade at all**, and once a cultivar's
  first product is approved its ladder is superseded, so every later CoQ for
  that strain has no grade either.
- No screen imports, approves, supersedes or selects a product. Nine of the ten
  product helpers in `api.js` have no caller; the tenth feeds the mother-bank
  dropdown, which needs an approved product that nothing in the app can create.
- The "product specification page" link points at `/qc/products/{id}/document`,
  a route that does not exist.
- The only visible potency import still loads the retired 71-strain ladders,
  and nothing stops a ladder being approved again next to approved products —
  two answers to one question, which the design doc itself forbids.

The plan's commit 2 ("Product A4 page + CoQ conformance") and commit 6
("Frontend QC") were never made. **PR #52's description says "conformance
replaces disposition" and describes the A4 product page; that overstated what
shipped, and I wrote it.** `docs/HANDOFF.md` repeats the error ("prints 'does
not conform'"). `docs/PRODUCT-CATALOGUE-2026-09.md` tells the truth in its
"Open" section.

Fix: build commits 2 and 6 as planned; add a product select to the compile form;
409 on approving a ladder whose cultivar has an approved product; implement or
remove the document route; correct HANDOFF and the PR body.

### 2.2 The pre-harvest-interval gate can be bypassed by the person recording the cut
`CS-01` · verified

`harvest.py:579` evaluates the spray block on whatever `harvested_on` the user
sends, and nothing rejects a future date. Posting the "clears on" date passes
the gate with no QA override, and the lot is written with a future harvest
date. A room move backdated to before the spray (`occurred_on` is also
unbounded, `cultivation.py:156`) lifts a room-scoped block the same way. The
module's own docstring says a recorder must not be able to wave away their own
block.

Fix: 422 when `harvested_on` or `occurred_on` is after the facility's today;
422 when a move is dated before the batch's current `phase_since`.

### 2.3 A retest can overturn a confirmed OOS
`QC-01` · verified

`coq_aggregation.py:357-373` lets any CLOSED OOS naming the test "cover" a
failing result that a later retest masked. It never reads the investigation's
outcome (`invalidated`, `lab_error`, `disposition`). A Phase II investigation
that confirmed the failure and rejected the batch still licenses the passing
retest, and the CoQ prints "Conforms to Specification". That is testing into
compliance.

Fix: cover a masked failure only with a CLOSED OOS that invalidated that result;
refuse to compile when any CLOSED OOS on the batch carries a REJECT disposition.

### 2.4 A CoQ stays approved and printable after a source certificate is voided or superseded
`QC-02` · verified

`void_certificate` never looks at `qc_coq_sources`; `review_coq` and
`render_coq` never re-check source status. Void iCoA A under §6.6, and the CoQ
compiled from A can still be approved and printed from A's snapshotted lines.

Fix: 409 in review/render when any source is not APPROVED/RELEASED; refuse or
flag a void/revision when the certificate is cited by a live CoQ; return each
source's live status.

### 2.5 Comma-decimal lab values are truncated, then graded as conforming
`QC-03` · verified

`parseFloat("0,6")` is `0` (`qcecoa-view.js:127,176`, `qccoa-view.js:256`), the
server trusts the number, and the laboratory's stored `decimal_separator` is
read by nothing. A lead result of "0,6 mg/kg" against a ≤ 0.5 limit is graded
`complies=true`, printed as "0,6" under "Conforms", and the verify step reports
VERIFIED. Macedonian-format certificates are the normal case here.

Fix: parse on the server from `raw_value` using the lab's separator; 422 when a
supplied numeric disagrees with the raw text; reject commas in the UI.

### 2.6 One login lockout bucket for the whole facility
`BC-01` · verified on the host

uvicorn trusts only the nginx container's address; nginx appends Traefik's
address to `X-Forwarded-For`; uvicorn 0.34 takes the rightmost untrusted
address, which is Traefik's for every request. The 30-failures-per-5-minutes
per-IP limiter (`auth.py:209`) is therefore one shared bucket: thirty wrong
passwords from anyone lock every user out of login, and tokens expire after 15
minutes with no refresh. Any successful login also clears that shared bucket,
so the limiter is not brute-force protection either. Login and request logs
record Traefik's address, not the client's.

Fix: add Traefik's network to `FORWARDED_ALLOW_IPS` (or `set_real_ip_from` in
nginx and forward `$remote_addr`); stop clearing the IP bucket on success.

### 2.7 Base users can read the organisation-wide weekly digest and AI report
`BC-02` · verified

`GET /ai/pins` restricts only the keys in `FUNCTION_ROLES`. The scheduler writes
the org-wide pins as `weekly_report` and `weekly_snapshot`
(`weekly_snapshot.py:486`), neither of which is in that map, so a plain USER —
and a department-scoped manager — can read every task, owner, overdue item and
declined assignment across the organisation. The July fix covered only
`next_week_plan`.

Fix: restrict by pin key (`weekly_report`, `weekly_snapshot`, `next_week_plan`)
when `subject_user_id` is null; extend the test.

### 2.8 Two batches of one strain cloned on the same day cannot both get plant IDs
`CS-02` · verified

Legacy plant IDs are `<date>_<cultivar>_<seq>` with `seq` per batch
(`plantids.py:66`), but `plants` is unique on `(org, plant_code)`. The second
batch's fill hits that constraint on its first chunk and returns 500 on every
retry (`cultivation.py:707-712` handles only the `(batch, seq)` conflict). Two
flowering rooms of one strain cloned together is the normal plan.

Fix: make the legacy ID unique by construction (`<date>_<batch code>_<seq>`),
after confirming the format with the owner.

### 2.9 A later-generation mother gets the wrong mother number
`CS-03` · verified

Registering generation 2 from parent `GP26_S1M03-1_001` with "mother no." left
blank stores `GP26_S1M05-2_001` — the next free number, and any campaign the
form has selected (`propagation.py:489-515` takes only `generation` from the
parent). The owner's convention keeps `S1M03` across generations. Segments
cannot be edited afterwards, and every clone later cut from that mother inherits
the wrong line.

Fix: with `parent_id`, take `campaign_id` and `mother_no` from the parent and
422 on contradiction; same in the form.

### 2.10 Any pull request runs as root on the production host
`DI-02` · verified

`ci.yml` runs on `pull_request` and every job runs on the single self-hosted
runner, which sits on the production host with the docker socket mounted and
host networking (`ops/gh-runner/compose.yaml`). A branch that edits `ci.yml`
and opens a PR can run `docker exec wwf-db-tasks psql …`. Agent sessions have
this reach already through the kvm4-runner, so the added exposure is anyone
else with push access, or a compromised branch. It also weakens the deploy
gate: "CI green at this commit" proves only that the `ci.yml` at that commit
passed.

Fix: run CI on a runner that does not share the production daemon (separate VM
or rootless), or require approval for PR runs; have `deploy.yml` verify the
`ci.yml` blob matches the default branch.

### 2.11 The 2026-09-18 tolerance decision was never implemented
`INS-03` (and `QC-14`, `INS-04`) · verified by grep

On 2026-09-18 the owner said the flat ±10 % grading "is not gonna work" and the
fitted tolerances apply everywhere. Nothing changed: `window_for` is ±10 %
(`plantids.py:35`), `imb_products.json` carries the ±10 % rule, and the facility
now holds two potency specifications with different numbers (Cap Junky grades
14/17/20/24/28 in the owner's finished specs vs 20/24/26/28 in `qc_products`;
CJ28 window top 29.59 % vs 30.79 %). `HANDOFF.md` turned the decision into an
open question. The 2026-09-06 out-of-grade rule (next grade, visual flag,
formal OOS, deviation to Cultivation and Production) is also not built.

Fix: record the decision; add a transactional ladder-level product create with
explicit windows and provenance; load the finished fitted specs as DRAFT
products for second-person approval; build the out-of-grade rule.

### 2.12 Stored cross-site scripting through a swab code
`FE-04` · verified

`decon-view.js:712` builds
`onclick="GF.WWF.deconSwabResultForm('${x.id}','${GF.esc(x.swab_code)}')"`.
`GF.esc` is HTML escaping; inside an inline JavaScript string the browser
decodes the entities back before the script runs, so a swab code containing a
quote breaks out and runs code when anyone clicks "Enter result". Reproduced in
jsdom by the reviewer. A QA manager could run script in an admin's session.

Fix: never put data in inline handlers; bind the click with `addEventListener`
and read the code from a `data-` attribute (the pattern the rest of the views
already use).

### 2.13 The chain of custody stops after one hop
`FE-02` · verified

The transfer form sends only `transfer_type`, `to_location` and a reason
(`qccustody-view.js:190-195`) — never `from_location` or `to_user_id`. The
backend's continuity guard (`custody.py:585-600`) anchors each transfer on the
previous entry's destination, so the second transfer for any sample is
rejected with 409. A field-to-lab chain cannot be recorded past its first step.

Fix: send the previous entry's destination as the origin (pre-filled,
read-only) and offer a recipient picker; the backend already does the rest.

### 2.14 Every timestamp is shown in UTC, one to two hours early
`FE-05` · verified

Views print the UTC string the backend sends
(`harvest-view.js:236`: `rei_until.slice(0,16).replace('T',' ')`); the
facility-zone formatter in `core.js` is used for dates only, and no view calls
a zone-aware date-time formatter. The pesticide re-entry line therefore reads
"no entry until 12:00" when the restriction lifts at 14:00 facility time. The
same applies to worklog sessions (typed 08:00, shown 06:00), e-signature and
custody times, waste witness times and inbox day grouping.

Fix: one `GF.fmtDateTime()` using `Intl.DateTimeFormat` with
`GF.facilityTZ()`, used everywhere a timestamp is printed.

### 2.15 Rooms and checks that can never be released
`FE-03`, `FE-10`, `BC-10` · verified

No button calls `POST /decon/cycles/{id}/fail`, so a cycle with a positive swab
cannot be failed, cannot be released, cannot take more steps, and blocks a new
cycle for that room in the same campaign. Biosecurity checks logged as pending
have no way to receive a result. Both routes exist on the backend and were
reviewed in July; the screens were never finished.

### 2.16 Cross-department handoffs cannot be accepted
`FE-06`, `BC-04` · verified

`departments.head_user_id` is never set, so the receiving department's manager
is never notified, and the task itself 404s for them under the scope guard —
while task owners and source-side managers see Accept/Reject buttons that
return 403.

Fix: set `head_user_id` on department create/update, and open the task to the
receiving department's manager while a handoff to it is pending.

## 9. Design observations

Patterns behind several findings, worth deciding on rather than patching one
