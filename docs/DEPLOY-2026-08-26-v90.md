## Migrations

Production was at tasks `0060` / users `0010`; this SHA carries tasks `0062`
and users `0011`.

Three pre-flight data checks were run against production **before** any DDL,
because two of the three migrations could have failed or broken the running
old version on real data:

| Check | Result |
| --- | --- |
| `profiles` case-insensitive username collisions (would abort users `0011`) | **0** collisions, 0 non-lowercase, 13 rows |
| `qc_oos_id_seq` still referenced by any column default (tasks `0062` drops it) | **none** |
| `qc_signatures` policy shape tasks `0061` expects to replace | exactly one `org_isolation` ALL policy |

### The chain was deliberately split around the image swap

The live **v89 actively calls `nextval('qc_oos_id_seq')`** (`qc/oos.py:214`)
when opening an OOS investigation; v90 replaced that with per-org numbering
and only mentions the sequence in a comment. Running the whole tasks chain to
head before the swap would therefore have left a window where the *running*
version 500s on OOS creation.

So the order was:

1. `tasks upgrade 0061` + `users upgrade head` — both verified
   backward-compatible with v89 (0061 keeps SELECT+INSERT, which is all v89
   does; 0011 is index-only). Live v89 re-checked healthy afterwards:
   `{"ready":true,"databases":{"users":"ok","tasks":"ok"}}`.
2. Swap backend + scheduler to v90.
3. `tasks upgrade head` (`0062`, drop the now-unused sequence).
4. Swap frontend, then docengine.

This removes the incompatibility window entirely rather than accepting it.

## Rollback path

Images `weekly_weed_flow-backend:v89`, `wwf-growflow:v129` and
`growflow-docengine:v20` are retained on the host, and
`/opt/wwf-deploy/snapshots/pre-c54fb57/compose.yaml.bak` restores the previous
tags. Note a rollback of the **tasks** chain past `0062` would need
`qc_oos_id_seq` recreated for v89 to open OOS investigations (that is exactly
what `0062`'s `downgrade()` does).
