# Production deploy: backend v92 + frontend v133 (2026-09-06)

Full-stack deploy from `cbfae38`, the head of PR #52. Production had fallen
**seven migrations behind** the branch — users `0011`, tasks `0063` — which is
what the nightly drift check had been red about since the department model
landed. This deploy closes that gap and puts four subsystems live at once.

## What shipped

- **`weekly_weed_flow-backend:v92`** (backend + scheduler, same image) —
  migrations `0064`–`0069` on the tasks chain and `0012` on the users chain,
  plus the routers they exist for: the department model, the propagation
  bank (mothers and clone runs), the official product catalogue with
  selection campaigns and trichome checks, and the as-built facility layout.
- **`wwf-growflow:v133`** — the redesigned navigation rail, the product
  catalogue and multi-batch journey views, the propagation views, and the
  Floor plan tab with its two representations (app-drawn SVG plan and the
  scanned sheet) over one register.

## The pending set is additive against production data

Checked rather than assumed. Across `0064`–`0069` and users `0012`, the only
destructive statements inside an `upgrade()` are three:

- `rooms_kind_check` and `profiles_role_check` are dropped and immediately
  re-added **wider** (clone room kinds; the `IR_MGR` role). A widened CHECK is a
  superset, so v91 keeps writing valid rows during the window between migrate
  and swap.
- `clone_runs.potency_spec_id` is dropped by `0067` — from a table that `0065`
  *creates in this same set*. It never existed in production and held nothing.

Everything else is `CREATE TABLE` / `ADD COLUMN`. That premise is what makes the
migrate-before-swap order safe, and it is why the order was kept.

It was additionally true, and worth recording, that `rooms`, `plants`,
`plant_batches` and `qc_coq` were all **empty** in production — the cultivation
subsystem has never been used live — so this schema change moved no rows at all.
`profiles` holds 14.

## Sequence as executed

1. Snapshot both databases, **verified** — `gzip -t`, dump-marker count, size
   floor. An unverified snapshot is not a rollback.
2. `compose.yaml` backed up, `cmp`-checked byte-identical.
3. `alembic -n users upgrade head` → `0012`; `alembic -n tasks upgrade head` →
   `0069`. **Before** the swap.
4. Image tags rewritten, each rewrite proved to have landed (a `sed` that matches
   nothing exits 0 — that is how a deploy reports success while production runs
   the old code).
5. `docker compose up -d --no-deps` **one service at a time**: `backend`, then
   `scheduler`, then `frontend`. No database service was touched, no `down`, no
   volume pruned.
6. Smoke.

## Rollback path

| item | value |
| --- | --- |
| database snapshot | `/opt/wwf-deploy/snapshots/20260906T141034Z-pre-v92-cbfae38/` |
| compose backup | `…/compose.yaml.pre-v92` |
| previous images | `weekly_weed_flow-backend:v91`, `wwf-growflow:v132` (both still on the host) |

Restore `compose.yaml` from the backup and `docker compose up -d --no-deps
backend scheduler frontend` to return to v91/v132. The schema is additive, so
v91 tolerates the migrated databases and a code-only rollback needs no database
work. Restoring the snapshot destroys every row written since 14:10 UTC and is
the last resort, not the first.

## Notes for the next session

- **Frontend was already at v132**, built 2026-09-04 and never recorded here, so
  this deploy went to **v133**. Read the running tag off the host before picking
  a version number; the docs directory is not a complete ledger of frontend
  deploys.
- **`/opt` is at 93 %, ~14 GB free** — tighter than the 80 % / 40 GB the
  operating notes record. Two image builds cost about a point. `docker system df`
  reports 23.87 GB reclaimable from images and 29.43 GB from volumes; the volumes
  figure is a trap (see `docs/DEPLOY.md` on `wwf_mass_letta_pgdata` and
  `wwf_mass_qms_*`) and old image tags are the rollback path, so neither is free
  space in any usable sense.
- **The kvm4-runner `/shell` endpoint takes `cmd`, not `script`.** A wrong key
  returns a bare **HTTP 422** that reads like an auth or availability problem.
  The authoritative request shape is the `kvm4.py` heredoc inside
  `.github/workflows/deploy.yml`.
- **Neither `curl` nor `wget` exists in the kvm4-runner container.** It runs
  `python:3.12-slim`, so `python3 -c` with `urllib` is the shortest path to an
  HTTP probe — no image pull, no `curl: not found` masquerading as a dead site.
- The nightly drift check should go green on its next run now that production is
  at both heads.
